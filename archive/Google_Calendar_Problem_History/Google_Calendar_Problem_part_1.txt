  Three caveats that matter

  - Pause alone isn't enough. Pausing stops dispatching, but new tasks keep
  piling into the queue, and the retries you saw are already queued. When you
  resume, that whole backlog fires at once and re-triggers the storm. That's why
  you pause and purge. The reconcile is idempotent and self-healing, so purged
  events just re-sync the next time someone touches them (or on a manual full
  sync) — you lose nothing permanent.
  - A firebase deploy --only functions will un-pause it. Deploying
  re-creates/updates the queue and resets it to running. That's actually what
  you want after the fix is live — but don't treat pause as durable across a
  deploy.
  - While paused, attendee syncs don't happen. New assignments won't show up on
  anyone's Google Calendar until you resume. Fine for a few hours; not something
  to leave paused for days.

  Why the account type is the actual ceiling

  The organizer that creates your events and sends the invites is

  What your code already does (and what it doesn't)

  planCalendarSyncTasks (calendar_sync_backend.ts:1161) already coalesces 
  duplicates within a single request — it Set-dedupes the event ids and pairs
  each with its delta, with a test at calendar_sync_backend.test.ts:393. So a
  bulk operation that touches event X five times in one handler invocation
  already produces one task.

  That means the 20–45× you saw is not intra-request. It's two other sources:
  1. Retries — retryConfig.maxAttempts: 5, so each task re-runs up to 5×. That's
  Fix #1's job (quota-aware backoff), not coalescing.
  2. Separate invocations over time — an assignment change at 10:00:01, another
  at 10:00:04, another at 10:00:07 are three distinct handler runs → three
  separate enqueueCalendarSync calls → three tasks. planCalendarSyncTasks never
  sees them together, so it can't dedupe them.

  #3 is specifically about collapsing #2 — the cross-invocation stream — into
  one reconcile after a short quiet period.

  The subtlety that kills the naive approach

  Each task carries a delta: AttendeeNotifyDelta = {addedMemberIds?, 
  removedMemberIds?} — the members to email for that change. So three rapid
  changes carry {added:[A]}, {added:[B]}, {removed:[C]}.

  If you collapse them with Cloud Tasks named-task dedup (name =
  sync-${eventId}), the 2nd and 3rd enqueues are rejected — only the first task
  runs, with delta {added:[A]}. The full-state reconcile still adds B to the
  calendar, but silently (B isn't in the surviving delta) → B never gets their 
  invite email. You'd be dropping notifications you meant to send. Plus Cloud
  Tasks won't let you reuse a task name for several minutes after one executes,
  so a change arriving right after a sync could be dropped entirely until the
  name frees. Two correctness bugs. That's why I'm walking it back.

  Coalescing has to merge deltas, not discard them.

  What I'd actually build: a debounced delta-accumulator

  A tiny per-event "pending" doc that accumulates the merged delta, drained by a
  single delayed task.

  Path A — on each change (replaces the direct enqueueCalendarSync):
  pendingRef = calendar_sync_pending/{env}_{eventId}
  transaction:
    p = read(pendingRef)
    merged.added   = union(p.added,   newDelta.addedMemberIds)
    merged.removed = union(p.removed, newDelta.removedMemberIds)
    write { delta: merged, dirty: true, updatedAt: now }
    if (!p.taskScheduled || lease expired):
       write { taskScheduled: true }
       enqueue ONE drain task, scheduleDelaySeconds = DEBOUNCE (~30s)
  Ten changes in 30s → the delta unions up, but only one drain task is enqueued.

  Path B — the drain task (replaces today's handler):
  transaction (claim):
    p = read(pendingRef)
    delta = p.delta
    write { dirty: false, delta: {}, taskScheduled: false }   // claim the work
  report = reconcile(eventId, delta)
  if report.failed (e.g. quota):        // ← this is where Fix #1 plugs in
    transaction: re-merge `delta` back in, set dirty:true
    re-enqueue drain with a LONG delay (post-quota-window)
  else if (pending became dirty during reconcile):
    enqueue another short drain            // changes that arrived mid-sync
  aren't lost

  The claim-then-reconcile-then-requeue-on-failure is the standard lease pattern
  — it guarantees no email intent is lost even if the reconcile throws, and
  changes landing mid-reconcile trigger exactly one more drain.

  Merge rule + the one edge case: merge = set-union of addedMemberIds and of
  removedMemberIds. The only wrinkle is a member added then removed inside the
  window (ends up in both lists). Resolve it last-writer-wins per member (the
  newer change wins its direction), or — cleaner — let the reconcile's own
  desired-vs-current diff decide invite-vs-cancel and treat the delta purely as
  "this member changed, notify them." Either is a few lines and unit-testable in
  isolation, like planCalendarSyncTasks already is.

  Tradeoffs to decide

  - Debounce window. ~30s is my default: near-total coalescing of a burst, and a
  30s delay before an assignment shows on someone's calendar is a non-issue for
  event scheduling. Longer = fewer syncs but more lag; shorter = snappier but
  less collapse.
  - Composes with #1. Coalescing cuts the number of reconciles (so quota is hit
  far less often), and #1 handles the reconciles that still fail. They share the
  pending doc as the single source of truth — clean fit, not competing
  mechanisms.
  - Cost: one small Firestore transaction per change + one per drain.
  Negligible, stays in free tier.

  Simpler fallback, if you want minimal change

  Keep named-task dedup only if you accept "calendar gets updated, emails are
  best-effort" — i.e., you're fine with the occasional dropped invite email and
  the name-reuse gap. Given your team's complaint is about emails, I wouldn't:
  silently dropping the email you meant to send is the wrong failure mode here.
