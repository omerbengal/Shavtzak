  Design — Chunk 1 of 2: Architecture & the staging layer

  Approach (and why)

  Three ways to represent "live DB + staged edits on top":

  - (A) Revive & repurpose the dormant overlay — recommended. The BLoC already
  has the merge routine that renders live DB slots with pending changes layered 
  on top (_pendingOperations + the merge at assignment_bloc.dart:~974). We keep 
  that rendering/merge logic, but replace its lifecycle: today a pending op
  auto-expires (5 min) and auto-clears when the DB stream confirms it. For
  staging, ops never expire and never auto-clear — they persist until
  Save-success, Discard, or revert-to-baseline.
  - (B) Build a fresh staging layer from scratch — more code, re-derives what
  already exists.
  - (C) Working-copy snapshot — violates your requirement #3 (screen must stay
  live).

  Going with (A): lowest risk, reuses battle-tested rendering, and the "changes
  on top of live DB" behavior you want is exactly what that merge already does.

  The staging model: per-slot desired-state, not an operation log

  Each staged edit is stored keyed by slot (slotKey = 
  eventId_roleType_slotIndex), one entry per slot. Editing the same slot five
  times just updates its one entry. This gives us three things for free:

  1. Revert = clean. If a slot's staged value returns to its DB baseline (you
  assign Dan, then put Ron back), the entry is dropped and that slot is no
  longer dirty. (Mirrors the constraints_screen "compare-to-original" pattern
  already in the app.)
  2. Deterministic Save. Save diffs desired vs baseline per slot → one create /
  update / delete each.
  3. Conflict detection (chunk 2) works by comparing the stored baseline against
  the current DB.

  Data shape

  A StagedAssignmentChange per touched slot:

  slotKey            // identity: eventId_roleType_slotIndex
  eventId, roleType, slotIndex
  desiredMemberId?   // null = staged-clear;  set = staged fill/swap
  desiredNotes, desiredLabelId, desiredAltPhone
  baselineAssignmentId?   // the DB assignment doc at first-touch (null if slot
  was empty)
  baselineMemberId?       // DB member at first-touch  → used for conflict
  detection
  baselineNotes/Label/AltPhone
  stagedAt

  - Held in a Map<slotKey, StagedAssignmentChange> in the BLoC. Dirty ⇔ map is 
  non-empty.
  - Cache: the map is serialized to JSON and written to localStorage under an
  env-prefixed key (e.g. test_assignments_staged_changes /
  assignments_staged_changes) via a new UserCacheService method — copying the
  exact jsonEncode/setString pattern ConfigCacheService already uses. Persisted
  on every change; loaded on screen init to rehydrate the overlay (your
  crash-recovery goal). Per-browser, per-environment.

  What changes in the per-edit flow

  Today each assign/clear does an immediate blocking Firestore write with a
  "מעדכן שיבוץ…" overlay. Under staging, an assign/clear/notes edit becomes an
  instant, in-memory + cache update — no DB write, no blocking overlay. That is
  the speed win you're after: the whole meeting is instant until the single
  Save. The blocking overlay only appears during Save itself.

  Still immediate (unchanged), per your scope choice: swipe-delete-a-slot
  (delete + quota↓), the manual-add wizard (create + quota↑), and the event-form
  modal. Consequence to be aware of: those three will still show today's brief
  spinner and hit the DB right away, while everything else is staged — a
  deliberate, mixed model. One derived rule: swipe-deleting a slot that has a 
  staged edit drops that staged entry (the slot is gone).

  Design — Chunk 2 of 2: Conflicts, Save, Leave-guard, UI

  1. Conflict taxonomy

  A staged slot conflicts whenever its stored baseline ≠ current DB (something
  changed the slot since you first touched it). Six types:

  #: A
  Type: המשרה נתפסה (slot taken)
  Situation: You filled/swapped to M; DB now shows a different member X
  דרוס DB (yours wins): write M over X
  קח מה-DB (drop yours): keep X
  ────────────────────────────────────────
  #: B
  Type: השיבוץ נמחק (target removed)
  Situation: Your swap/notes edit points at an assignment the DB no longer has
  (now empty)
  דרוס DB (yours wins): re-create as M
  קח מה-DB (drop yours): accept the deletion
  ────────────────────────────────────────
  #: C
  Type: התנגשות בניקוי (clear-collision)
  Situation: You cleared B; DB now holds a different member X
  דרוס DB (yours wins): delete X (apply clear)
  קח מה-DB (drop yours): keep X
  ────────────────────────────────────────
  #: D
  Type: המשרה בוטלה (slot vanished)
  Situation: Quota shrank; your slotIndex no longer exists
  דרוס DB (yours wins): (see note)
  קח מה-DB (drop yours): drop your change
  ────────────────────────────────────────
  #: E
  Type: החבר לא זמין (member gone)
  Situation: Member you assigned was deactivated/deleted
  דרוס DB (yours wins): assign anyway (deactivated only)
  קח מה-DB (drop yours): drop your change
  ────────────────────────────────────────
  #: F
  Type: הערות/שיבוץ שונו (notes re-owned)
  Situation: Your notes edit collides with a DB notes change, or the member
  changed under your notes edit
  דרוס DB (yours wins): apply your notes
  קח מה-DB (drop yours): keep DB

  sub-decision I need from you (below).

  3. Save flow

  1. Press שמור.
  2. Recompute conflicts (baseline vs current DB) across all staged slots.
  3. If any conflicts → one consolidated resolution dialog: a scrollable list,

  The write architecture (what I got wrong in the spec)

  Every assignment write — create, update, delete — does not touch Firestore

  honor the atomic, all-or-nothing Save you chose, the batch has to be atomic
